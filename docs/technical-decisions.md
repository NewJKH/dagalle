## 1. JWT 무상태 인증 + Redis refresh 토큰

**배경**
로그인 상태를 유지해야 하는데, 서버를 여러 대로 늘릴 수 있는 구조를 원했다. 전통적 세션 방식은
로그인 상태가 특정 서버 메모리에 묶여 있어 스케일아웃 시 "세션이 어느 서버에 있나" 문제가 생긴다.

**결정**
Spring Security를 `SessionCreationPolicy.STATELESS`로 설정하고 JWT 기반 인증을 채택했다.
요청마다 `JwtAuthenticationFilter`가 토큰을 검증한다.

**장점**
- 서버가 세션 상태를 들고 있지 않으므로 **수평 확장이 자유롭다.**
- 토큰 자체에 신원이 담겨 있어 인증을 위한 DB/세션 조회가 필요 없다.

**트레이드오프**
- JWT는 한 번 발급하면 만료 전까지 유효해서 **즉시 무효화(로그아웃·탈취 대응)가 어렵다.**
- access 토큰 수명을 길게 잡으면 보안 위험, 짧게 잡으면 사용자가 자주 끊긴다.

**보완**
- access 토큰은 짧게(30분), refresh 토큰은 길게(7일) 분리.
- refresh 토큰을 **Redis에 TTL과 함께 저장**해서, 로그아웃 시 서버에서 토큰을 삭제하면
  재발급을 막을 수 있다 → 무상태의 약점을 부분적으로 보완.
- 로그인 API에는 `LoginRateLimiter`로 무차별 대입 차단.

**코드 위치**
- `common/security/SecurityConfig.java:37` (STATELESS)
- `common/security/JwtAuthenticationFilter.java`, `JwtTokenProvider.java`, `LoginRateLimiter.java`
- `common/token/TokenStore.java` (+ Redis/InMemory 구현)

**면접 포인트**
"무상태의 확장성을 취하되, JWT의 본질적 약점인 즉시 무효화 불가를 refresh 토큰을 Redis에서
관리하는 방식으로 보완했다"는 트레이드오프 인식을 보여줄 수 있다.

## 2. WebSocket 실시간 협업 편집

**배경**
팀 여행 기능에서 **여러 명이 동시에 같은 일정을 보고 편집**한다. REST만 쓰면 남이 바꾼 내용을
보려면 새로고침해야 하는데, 협업 편집 UX로는 부적절했다.

**결정**
STOMP over WebSocket(`/ws`, SockJS 폴백)을 도입. 한 명이 일정을 수정하면
`WebSocketEventPublisher`가 `/topic`으로 변경을 브로드캐스트해 다른 멤버 화면에 즉시 반영한다.
채팅도 같은 채널을 사용한다.

**장점**
- 폴링 없이 **변경이 실시간 전파**된다.
- 채팅·일정 동기화를 하나의 통신 인프라로 통합.

**트레이드오프**
- WebSocket은 연결 후 계속 열려 있는 통로라 **일반 REST 보안 필터 체인을 타지 않는다.**
  → 인증 공백이 생길 수 있다.
- 연결 상태 관리(재연결 등) 부담이 REST보다 크다.

**보완**
- `JwtChannelInterceptor`로 **STOMP 핸드셰이크 시점에 JWT를 검증**해 인증 공백을 막았다.
  (REST는 필터, WebSocket은 채널 인터셉터로 인증 경로를 이원화)
- 프론트는 `@stomp/stompjs` + `sockjs-client`로 브라우저 호환성 확보.

**코드 위치**
- `common/websocket/WebSocketConfig.java` (엔드포인트·브로커)
- `common/websocket/JwtChannelInterceptor.java` (핸드셰이크 인증)
- `common/websocket/WebSocketEventPublisher.java`
- `domain/plan/service/PlanRouteService.java`의 `publishDayUpdate()` (실제 브로드캐스트 호출)
- 프론트: `frontend/src/hooks/useWebSocket.ts`

**면접 포인트**
"REST와 WebSocket은 인증이 적용되는 지점이 다르다"는 점을 인지하고, 두 경로에 각각
인증 장치를 둔 것 — 흔히 놓치는 보안 공백을 메운 사례.

## 3. 트러블슈팅 — 교통비 오류와 "AI 값을 믿지 않는" 설계

**증상**
일본 여행 일정에서 **도보 이동에 1,400원, 지하철에 600원** 같은 말이 안 되는 교통비가 표시됐다.

**원인 분석**
일정 생성 시 Claude가 내려준 JSON의 `estimatedCost`(교통비 추정값)를 **그대로 DB에 저장**하고
있었다. LLM은 비용 같은 수치를 자주 틀리게(할루시네이션) 내놓는데, 그 값을 검증 없이 신뢰한 것이
근본 원인이었다.
- 도보는 원래 0원이어야 하는데 LLM이 임의 금액을 넣음.
- 일본 지하철은 **거리별 요금제**인데 LLM이 한국식·임의값으로 답함.

**결정**
"교통비는 LLM이 아니라 코드가 계산한다"로 정책을 바꿨다. 저장 시점에 교통수단별로 분기:
- `WALK` → 무조건 0원 (AI 값 무시)
- `SUBWAY` / `BUS` / `TRAIN` → `TransitFareRegistry`가 국가·거리 기반으로 **강제 재계산**
- `CAR` / `ETC` → AI 추정값 유지(주차·톨비 등은 규칙화가 어려움)

국가별 요금은 **전략 패턴**으로 분리했다. `TransitFareCalculator` 인터페이스를 두고
`KoreaTransitFareCalculator`, `JapanTransitFareCalculator`를 구현, `TransitFareRegistry`가
국가코드로 적절한 계산기를 선택한다. 일본은 도쿄메트로/JR의 **거리 구간별 엔화 요금 × 환율**로
근사 계산한다.

**장점**
- 비용 신뢰도가 회복됐고, 새 국가를 추가할 때 계산기 클래스 하나만 더 만들면 된다(OCP).

**트레이드오프 / 남은 한계**
- 엔/원 환율을 **×9로 고정**해 두어, 환율 급변 시 오차가 생긴다.
- 거리는 좌표 기반 직선거리(Haversine)라 실제 노선 거리와 차이가 있다.

**보완 방향**
- 환율을 외부 API로 동적 반영하거나 설정값으로 분리.
- 이미 Google Routes로 실거리를 받는 경로는 그 값을 우선 사용.

**코드 위치**
- `domain/ai/service/AiScheduleService.java` `savePlanDay()` (수단별 분기 저장)
- `domain/plan/fare/TransitFareCalculator.java` (전략 인터페이스)
- `domain/plan/fare/KoreaTransitFareCalculator.java`, `JapanTransitFareCalculator.java`
- `domain/plan/fare/TransitFareRegistry.java` (국가별 선택)

**면접 포인트**
LLM을 쓰되 **"LLM이 잘하는 일과 못하는 일을 구분"**한 사례. 창의적 일정 구성은 AI에게,
정확해야 하는 수치 계산은 결정론적 코드에게 맡겼다. + 전략 패턴으로 확장성까지 확보.

## 4. AI 호출 비용·지연 최적화

**배경**
Claude API는 호출당 비용·지연이 발생한다. 일정 생성 전 과정을 전부 LLM에 맡기면
비싸고 느리다.

**결정**
LLM이 꼭 필요한 부분과 규칙으로 처리 가능한 부분을 나눴다.
- **규칙 기반**으로 처리: 여행 제목, 렌트카·숙박 스켈레톤 생성, 자연어 입력 파싱.
- **Claude 호출**: 실제 Day별 상세 일정 생성 등 "창의성·지식"이 필요한 부분만.

**장점**
- 불필요한 LLM 호출 제거로 **비용·지연 감소.**
- 규칙 처리 부분은 결과가 결정론적이라 디버깅·테스트가 쉽다.

**트레이드오프**
- 규칙 코드가 늘어 유지보수 대상이 증가.
- 규칙과 LLM 결과의 형식을 맞추는 접합부 관리가 필요.

**보완**
- 일정 생성 정책을 `AiScheduleService` 한 곳에 모아 호출 경계를 명확히 함
  (전체 일괄 생성 / 단건 재생성 / 빈 시간 채우기로 호출 시나리오를 구분).
- 모델은 작업 난이도에 맞춰 선택(현재 `claude-sonnet-4-5`)하고, 설정값으로 분리해 교체 가능.

**코드 위치**
- `domain/ai/service/AiScheduleService.java` (클래스 상단 주석에 호출 정책 명시)
- `domain/ai/client/ClaudeApiClient.java` (모델·토큰 등 호출 캡슐화)
- 모델 설정: `application.yml` / `application.properties`의 `claude.model`

**면접 포인트**
"AI를 쓴다 = 다 AI에 맡긴다"가 아니라, **비용·정확도·속도를 고려해 AI와 규칙의 역할을 분담**한
설계 감각.

## 5. 무거운 점수 계산을 배치(cron)로 분리

**배경**
맛집 추천 점수는 평점·리뷰수·트렌드를 종합해 계산하는데, 전체 식당을 도는 무거운 작업이다.
사용자 요청마다 실시간 계산하면 응답이 느려진다.

**결정**
점수 계산을 **스케줄러 배치**로 분리했다. `@Scheduled(cron = "0 0 3 * * *")`로
트래픽이 적은 **매일 새벽 3시**에 전체 점수를 재계산해 `RestaurantScore`에 저장하고,
조회 시에는 저장된 값을 빠르게 내준다.

**장점**
- 사용자 조회 응답이 빠르다(미리 계산해 둠).
- 무거운 연산을 한가한 시간대로 이동.

**트레이드오프 / 현재 한계**
- 점수가 **최대 하루 지난 값**일 수 있다(실시간성 ↓ — 추천에선 허용 가능한 수준).
- 더 솔직한 한계: 현재 `positiveRatio = 0.75`, `recentTrend = STABLE`이 **하드코딩**이다.
  코드 주석에도 "실제로는 외부 리뷰 API에서 가져와야 함"이라고 남겨 두었다.
  → 배치 구조와 점수 공식은 완성됐지만, 입력 데이터는 아직 미완성.

**보완 방향**
- 외부 리뷰/감성분석 API를 연동해 `positiveRatio`·`recentTrend`를 실제 값으로 채우기.
- 변경이 있는 식당만 재계산하는 증분 배치로 비용 절감.

**코드 위치**
- `domain/restaurant/scheduler/RestaurantScoreScheduler.java`
- `DagalleApplication.java`의 `@EnableScheduling`
- `domain/restaurant/entity/RestaurantScore.java` (점수 공식)

**면접 포인트**
"실시간 계산 vs 사전 계산"의 트레이드오프를 판단한 사례. + 미완성 부분을 숨기지 않고
주석으로 한계와 개선 방향을 남긴 점(정직한 엔지니어링).

## 6. 인터페이스 추상화로 구현 교체 가능하게

**배경**
환경(로컬/운영)이나 대상(국가)이 달라질 때 코드 본문을 고치지 않고 구현만 바꾸고 싶었다.

**결정**
변하는 부분을 인터페이스 뒤로 숨기는 추상화를 두 곳에 적용했다.
- `TokenStore` 인터페이스 → `RedisTokenStore`(운영) / `InMemoryTokenStore`(로컬·Redis 미사용).
- `TransitFareCalculator` 인터페이스 → 국가별 구현 + `TransitFareRegistry`로 선택(3번 참고).

**장점**
- 운영은 Redis, 로컬은 인메모리로 **인프라 의존 없이 개발** 가능(로컬에선 Redis 자동설정 제외).
- 새 국가/저장소 추가 시 기존 코드 수정 없이 구현 클래스만 추가(OCP·DIP).

**트레이드오프**
- 추상화 계층이 늘어 단순 기능 대비 코드량이 증가.
- 과한 추상화는 오히려 읽기 어렵다 → "정말 바뀌는 축"에만 적용.

**보완**
- 실제로 교체가 일어나는 축(저장소 환경, 국가)에만 한정 적용해 과설계를 피함.

**코드 위치**
- `common/token/TokenStore.java` (+ `RedisTokenStore`, `InMemoryTokenStore`)
- `domain/plan/fare/TransitFareCalculator.java` (+ Registry)
- 로컬 프로파일 Redis 제외: `application.yml`의 `local` 프로파일 `autoconfigure.exclude`

**면접 포인트**
디자인 패턴을 "외워서 쓴" 게 아니라, **변동성이 큰 지점을 식별해 거기에만** 전략 패턴·
의존성 역전을 적용했다는 판단 근거를 설명할 수 있다.

## 7. 트러블슈팅 — 구글 지도 경로 실패와 폴백 체계

> 지도에서 두 장소를 잇는 선이 일부 구간에서 그려지지 않던 문제를, 외부 경로 API에
> 단계적 폴백을 두어 해결한 사례.

**🟢 쉽게 말하면 (비개발자용)**
> 여행 일정의 장소들을 지도 위에 선으로 이어 보여주는데, 이 "선 그리기"를 구글 지도에
> 맡겼다. 그런데 구글이 **일본 지하철 같은 일부 구간은 길을 못 찾아서** 선이 빵꾸 나
> 끊겨 보였다. 그래서 **"구글이 실패하면 다른 방법으로라도 선은 무조건 그린다"**는
> 안전장치(= 폴백)를 만들었다. 구글이 안 되면 다른 무료 길찾기 서비스로, 그것도 안 되면
> 최소한 두 점을 직선으로라도 이어서 — **어떤 경우에도 빈 지도가 안 나오게** 했다.
>
> *(아래는 같은 내용을 기술적으로 자세히 적은 것)*

### 1) 선택 배경

일정의 장소들을 지도에 선으로 이어 보여주는 기능을 구글 지도
`DirectionsService`로 구현했다. 두 지점을 주면 실제 도로·노선 모양대로 경로를 그려주는
API다.

그런데 일부 구간에서 **선이 아예 그려지지 않는** 현상이 있었다. 특히 다갈래의 주력
시장인 **일본의 대중교통(지하철·기차) 구간과 일부 도보 구간**에서 자주 나타났다.

원인을 좁혀 보면, `DirectionsService`가 항상 경로를 돌려주지는 않는다는 점이었다.
호출 결과로 `OK`가 아닌 상태(구글이 경로를 찾지 못하면 결과 0건 상태를 반환)가
내려오면, 렌더러에 넣을 경로가 없어 선이 그려지지 않았다. 그 배경에는:

- **대중교통 데이터 커버리지 편차** — 구글이 모든 노선의 시간표 데이터를 갖고 있지
  않아, 일본 사철 등 일부 구간은 경로를 찾지 못했다.
- **출발 시각 미전달** — 대중교통 경로는 출발 시각이 중요한데, 요청에 `departureTime`을
  넣지 않아 "현재 시각" 기준으로 계산됐다. 운행이 없는 시간대면 결과가 없었다.
- **도보의 물리적 한계** — 거리가 멀거나 보행로가 없는 구간은 경로가 없었다.

즉 **외부 경로 API의 결과를 "항상 성공한다"고 전제**한 게 문제였다. 우리 데이터(일본
대중교통)와 구글 커버리지가 어긋나는 지점에서 화면이 비었다.

> **관측 근거** — 도쿄 2일 일정(지하철·기차·도보 혼합)으로 재현한 결과, 브라우저 콘솔에
> 구글 SDK가 남긴 `Directions request returned no results.` 메시지가 **경로 요청 8건에서
> 확인**됐다. 실패 원인 코드를 코드에서 따로 로깅하지는 않으므로 전 구간을
> `ZERO_RESULTS`로 단정하지는 않고, 구현은 "**`OK`가 아닌 응답이면 폴백**"으로 처리했다.

### 2) 해결방안 / 의사결정

"외부 API는 실패할 수 있다"를 전제로 바꾸고, 경로 렌더링에 **단계적 폴백**을 직접
넣었다. `DirectionsService` 콜백에서 상태가 `OK`가 아니면 폴백 핸들러로 분기한다.

교통수단의 성격에 따라 처리를 갈랐다. **도보·자동차는 "실제 경로"가 의미 있고,
지하철·기차는 애초에 이용자가 도로를 따라가지 않으므로 "구간 표현"이면 충분**하다는
판단이다.

```
[도보 · 자동차]  실제 경로가 중요 → 단계적 폴백
  1순위  구글 DirectionsService  → 실제 도로·보행로 (거리·시간까지 사용)
    ↓  OK 아님
  2순위  OSRM (무료 오픈소스 길찾기) → 실제 도로 경로
    ↓  실패
  3순위  두 지점 직선 연결

[지하철 · 기차]  노선 데이터 없음 → 역↔역 점선 곡선으로 표현 (외부 호출 없음)
```

> 용어: **DirectionsService** = 구글의 길찾기 기능, **OSRM** = 구글 대신 쓸 수 있는
> 무료 길찾기 서비스, **폴백(fallback)** = 1순위가 실패하면 자동으로 차선책으로 넘어가는 것.

의사결정의 핵심은 **"정확도를 단계적으로 양보하더라도, 선은 반드시 그린다"**였다.

- **도보·차량**: 구글이 실패하면 OSRM에 다시 요청해 실제 도로 경로를 받아왔다. OSRM은
  경로를 압축된 문자열로 주는데, 이를 좌표로 푸는 변환기(polyline 디코더)를 직접 구현했다.
- **지하철·기차**: 실제 노선을 그리려면 교통사가 공개하는 GTFS(대중교통 표준 데이터)의
  `shapes` 같은 노선 좌표가 필요한데, 일본 사철은 공개·라이선스가 제각각이라 도입 비용이
  컸다. 또 OSRM은 도로·보행로 전용이라 철길을 대신 그릴 수 없다. 그래서 **정확한 선형을
  포기하는 대신, 역↔역을 2차 베지어 곡선으로 이어 점선 처리**했다. 도로를 억지로 따라가
  "전철이 도로로 다니는 것처럼" 보이는 오해를 없애고, 구간과 방향만 명확히 전달한다.
  소요시간은 AI가 만든 일정값(`durationMinutes`)으로 채웠다.
- **엉뚱한 선 잔상 방지**: 날짜(Day)를 빠르게 전환하면 이전 날짜의 길찾기 응답이 뒤늦게
  도착해 엉뚱한 선이 남는 문제가 있어, 날짜를 바꾸면 진행 중이던 요청을 취소하도록 했다
  (`AbortController`).
- **백엔드도 동일 사상**: `GoogleRoutesClient`는 호출 실패 시 `null`을 반환하고, 거리는
  좌표 기반 직선거리(Haversine)로 폴백한다.

### 3) 성과

- **"빈 지도"가 구조적으로 사라졌다.** 도보·차량은 마지막 단계에서 직선을, 대중교통은
  곡선을 항상 그리므로 선이 아예 없는 구간이 나오지 않는다.
- **주력 시장의 깨짐을 해결했다.** 구글 경로가 가장 자주 비던 일본 대중교통 일정에서도
  경로가 끊겨 보이지 않게 됐다. (도쿄 2일 일정으로 재현·확인)
- **정확도를 등급으로 관리하게 됐다.** 도보·차량은 구글(실노선) → OSRM(실도로) →
  직선 순으로 가능한 만큼 정확하게 낮춰가고, 폴백 구간은 거리 대신 AI 예상 시간을 채워
  정보 공백도 메웠다.
- **표현이 실제와 어긋나지 않게 됐다.** 대중교통을 도로 경로로 근사하면 "전철이 도로로
  다니는" 잘못된 인상을 준다. 곡선 점선으로 바꿔 **정확하지 않다는 사실 자체가 드러나는**
  표현을 택했다 — 틀린 정보를 정확한 척 보여주지 않는 쪽이 낫다는 판단.

**한계 (정직하게)**
- 대중교통 곡선은 실제 노선이 아니다. 구간·방향만 전달하며 거리는 표시하지 않는다.
- 도보·차량의 마지막 직선 폴백도 실제 경로와 달라 거리·모양이 부정확하다.
- OSRM 공개 서버는 SLA가 없어 운영 트래픽에는 부적합하다 — 실서비스라면 자체 호스팅
  또는 결과 캐싱이 필요하다.
- 더 근본적으로는, 대중교통 요청에 실제 출발 시각(`departureTime`)을 넘기면 구글 경로가
  성공할 여지가 있다 — 성공 시 실제 노선이 그려지므로 남은 개선 과제다.

**코드 위치**
- `frontend/src/components/MapView.tsx` — 단계적 폴백, 베지어 곡선(`curvePoints`),
  점선 렌더링(`drawTransitCurve`), polyline 디코더, AbortController
- `frontend/src/pages/MapDemoPage.tsx` — 로그인·백엔드 없이 지도를 검증하는 데모 화면
- `src/main/java/org/jkh/com/dagalle/domain/plan/client/GoogleRoutesClient.java` — 실패 시 null·직선거리 폴백

**면접 포인트**
"외부 API(구글 지도)를 항상 성공한다고 전제하지 않고, **`OK`가 아닌 응답에 단계적
폴백**을 두어 화면 안정성을 확보했다." 교통비(3번)와 같은 철학 — **외부에서 받은 결과를
무조건 신뢰하지 않고 보정한다.**

> 참고: 회색 지도(컨테이너 크기 0), 스크립트 중복 로딩, 마커 중복도 같은 맥락에서
> 각각 `ResizeObserver`·싱글톤 로더·좌표 키 dedup으로 방어했다. (상세는 코드 주석 참고)

## 8. 죽어 있던 추천 기능을 이벤트 기반으로 살리기

> 백엔드만 있고 화면에 연결되지 않아 아무도 쓰지 않던 맛집 추천 기능을, 사용자 별점을
> 입력으로 붙여 실제로 동작하는 기능으로 만든 사례.

**🟢 쉽게 말하면 (비개발자용)**
> 맛집 점수를 매일 새벽에 계산해 저장하고 있었는데, **정작 그 점수를 보여주는 화면이
> 없었다.** 게다가 점수 재료가 구글 데이터뿐이라 우리 서비스만의 값이 없었다. 그래서
> **여행을 다녀오면 그 식당에 별점을 남기고**, 그 별점이 곧바로 점수에 반영돼
> **일정 화면에서 "이 근처 맛집"으로 보이도록** 연결했다.

### 1) 선택 배경

맛집 추천은 새벽 배치(5번 참고)가 점수를 계산해 `restaurant_scores`에 저장하고,
`GET /restaurants/recommend`로 조회하는 구조였다. 그런데 점검해 보니 문제가 세 겹이었다.

- **아무도 호출하지 않았다.** 프론트엔드 전체에서 이 API를 부르는 화면이 없었다.
  배치는 매일 돌지만 결과를 볼 방법이 없는 **죽은 기능(dead feature)** 이었다.
- **사용자 신호가 없었다.** 점수 입력값이 구글 평점·리뷰 수뿐이라, 차별화된 추천이
  아니었다. 게다가 긍정 비율은 `0.75`로 하드코딩돼 있었다.
- **조회 쿼리가 사실상 결과를 못 냈다.** `WHERE is_open_now = true` 조건 때문에 값이
  NULL인 장소(AI가 만든 대부분)가 통째로 제외됐고, **거리 필터가 아예 없어** "근처"가
  아니라 전역 상위 점수가 나오는 구조였다.

### 2) 설계 / 결정사항

**갱신 방식을 신호의 성격에 따라 나눴다.** 이게 핵심 결정이다.

| 신호 | 변경 시점을 아는가 | 갱신 방식 |
|------|-----------------|----------|
| 구글 평점 | 모른다 (외부에서 조용히 바뀜) | 주기적 **전체 배치** |
| 사용자 별점 | **안다** (누르는 순간이 이벤트) | 해당 식당만 **즉시 갱신** |

- **이벤트 기반 단건 갱신**: 별점을 남기면 그 식당의 별점만 집계해
  (평균 평점, 4점 이상 비율) 해당 `RestaurantScore` 하나만 재계산한다. 전체 배치를
  기다리지 않고, 사용자 수가 늘어도 갱신 비용이 식당 1건으로 고정된다.
- **권한 제한**: 별점은 **"내 완료된 여행 일정에 포함된 장소"**에만 남길 수 있게 막았다.
  안 가본 곳에 점수를 주면 추천 신뢰도가 무너지기 때문이다.
  (`existsVisitedByUser` — 완료 여행 + 멤버 + 해당 장소 포함 여부를 한 번에 확인)
- **조회 쿼리 교정**: 거리 필터(기본 반경 3km)를 추가하고, `is_open_now`로 **제외하지 않고
  정렬에만 반영**하도록 바꿨다. 여행은 미래 시점이라 "지금 영업 중"으로 거르는 건 틀렸다.
- **화면 연결**: 일정의 장소를 펼치면 그 좌표 기준 "이 근처 맛집"이 추천 점수와 함께
  뜨고, 완료된 여행의 식당에는 별점 입력이 나타난다. 배치 → 별점 → 추천이 한 화면에서
  이어진다.

### 3) 성과

- **죽어 있던 기능이 실제로 동작하게 됐다.** 배치 결과가 처음으로 사용자 화면에
  노출되고, 별점이 그 점수에 반영된다.
- **서비스 고유 데이터가 생겼다.** 구글 평점을 그대로 쓰는 게 아니라 **"실제 다녀온
  사람들의 평가"**라는, 다갈래에만 있는 추천 근거를 확보했다.
- **갱신 비용이 사용자 수와 분리됐다.** 별점 1회 = 식당 1건 갱신이므로, 평가가 아무리
  늘어도 전체 재계산이 필요 없다.
- **빈 결과가 나오던 조회 버그를 잡았다.** 거리 필터와 `is_open_now` 처리를 고쳐
  "근처"가 실제로 근처를 의미하게 됐다.

**한계 (정직하게)**
- 초기에는 별점 데이터가 없어 추천 목록이 비어 있다(콜드 스타트). 이때는 "아직 평가된
  맛집이 없다"는 안내를 노출한다.
- 배치 쪽 `positiveRatio = 0.75` 하드코딩은 여전히 남아 있다. 별점이 쌓인 식당은
  실제 값으로 덮이지만, 그 외에는 고정값이다.
- 별점 1개만 있어도 평균이 만점이 될 수 있다 — 표본 수를 반영한 보정(베이지안 평균 등)이
  다음 과제다.

**코드 위치**
- `domain/restaurant/entity/RestaurantReview.java` — 사용자-식당 별점 (조합당 1건)
- `domain/restaurant/service/RestaurantService.java` — `rateRestaurant()` 이벤트 기반 갱신 + 권한 검증
- `domain/restaurant/repository/RestaurantScoreRepository.java` — 거리 필터 조회 쿼리
- `domain/plan/repository/PlanRouteRepository.java` — `existsVisitedByUser` 방문 검증
- `frontend/src/pages/TravelPlannerPage.tsx` — `StarRating`, `NearbyRestaurants`

**면접 포인트**
"기능이 있는데 안 쓰이는 이유를 추적했더니 **화면 미연결 + 입력 데이터 부재 + 쿼리 버그**
세 겹이었다. 이때 **외부 데이터는 배치, 내부 이벤트는 즉시 갱신**으로 갱신 전략을 신호
성격에 맞게 분리한 것이 핵심 결정이었다."
